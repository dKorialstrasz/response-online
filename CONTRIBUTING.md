# Участие в разработке Response Online

## Обязательная трассируемость

Любая работа Milestone 1 начинается с открытой issue из [roadmap M1](https://github.com/users/dKorialstrasz/projects/1/views/1). Нельзя начинать изменение по устной договорённости или ссылаться только на родительский epic #1.

Каждая roadmap issue должна содержать:

- ID требований из `docs/requirements/milestone-1.md`;
- измеримые acceptance criteria;
- приоритет P0/P1/P2/P3;
- роль-владельца, зависимости и ожидаемое evidence;
- для карточной работы — `cardId`/`abilityId`, источник и verification status.

## Ветки, коммиты и pull requests

Ветка создаётся от актуальной `main` и включает номер конкретной roadmap issue:

- `feature/<issue>-short-name`;
- `fix/<issue>-short-name`;
- `docs/<issue>-short-name`;
- `test/<issue>-short-name`;
- `ci/<issue>-short-name`.

Коммиты следуют Conventional Commits и заканчиваются trailer-ссылкой:

```text
feat(engine): validate action budget

Refs #10
```

Исправление, которое должно закрыть issue после merge, использует `Fixes #<issue>`. Каждый коммит должен относиться хотя бы к одной конкретной roadmap issue. Ссылка только на #1 недостаточна.

PR обязан:

1. ссылаться на конкретную issue через `Refs #N` или `Fixes #N`;
2. перечислять затронутые Requirement IDs и зависимости;
3. показывать acceptance evidence и результаты подходящих проверок;
4. обновлять схемы, тесты, ADR/rulings и документацию, если затронуты контракты;
5. не смешивать независимую работу или незавершённые чужие изменения.

В текущем solo-процессе все роли и решения принадлежат владельцу проекта; ChatGPT действует только как исполнитель. Поэтому фиктивный «независимый review» не заявляется. Перед merge обязательны:

- self-check исполнителя с зафиксированными результатами;
- зелёные обязательные проверки CI;
- разрешение всех обсуждений;
- явная пользовательская приёмка владельцем проекта;
- для правил и контента — явная проверка и решение владельца в соответствующей роли.

Merge выполняется только после отдельного согласования владельца. Default strategy — squash merge; squash message также содержит ссылку на issue. Если в проекте появится иной уполномоченный reviewer, переход к независимому review оформляется отдельным изменением процесса.

## Изменение scope, правил и контента

Scope change оформляется отдельной issue с влиянием на сроки, тесты, риски и публикацию. Архитектурное решение требует ADR; неоднозначность официального правила требует ruling/ответа правообладателя. ADR не заменяет официальный ruling.

Неподтверждённые поля карт остаются `unknown`; их нельзя заменять догадкой, нулём или привычной механикой другой ККИ. Изменения контента обязаны обновлять provenance/evidence и выпускать новую `contentVersion`.

## Definition of Done

Issue закрывается только после реализации, подходящих тестов, self-check, пользовательской приёмки, обновления контрактов/документации, зелёного CI и ссылки на evidence. Milestone 1 закрывается только по локальным критериям AC-01–11; отдельные завершённые задачи не компенсируют незакрытую колоду или core-зависимость. Публичное развёртывание, права на публикацию и GamePix имеют отдельные будущие ворота и не считаются выполненными в M1.

## Локальная проверка приложения

После `make bootstrap` обязательный self-check приложения запускается командами:

```bash
make check
make dependencies
bash tests/smoke/local_backend.sh
make manifest
```

CI повторяет форматирование/линтеры, Go unit и race tests, TypeScript
typecheck/tests/build, schemas, content, secrets и dependency audit. Артефакт сборки
содержит commit SHA и хеши. Docs CI отдельно проверяет Markdown consistency,
трассируемость решений и арифметику manifests.

Для `main` требуются зелёные проверки Application CI и Docs CI, отсутствие
неразрешённых обсуждений и явная пользовательская приёмка. Если тариф или права
GitHub не позволяют применить branch protection, ограничение фиксируется в Issue
и PR; оно не подменяется заявлением о включённой защите.
