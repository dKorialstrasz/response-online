## 1. Назначение и правила чтения

Документ определяет результат M1, договорённости между продуктом, разработкой и QA, границы реализации и условия выпуска. Он не утверждает, что игра или интеграции уже реализованы. На момент подготовки в репозитории есть только исходный README; исходного приложения, карточной базы, CI и автоматизированных тестов нет.

«Должен» означает обязательное требование. «Рекомендуется» означает рекомендацию, от которой можно отступить с обоснованием. Требования с префиксами FR, DATA, RULE, NET, SEC, NFR, OPS, GP и PROC проверяются до приёмки соответствующего этапа. Численные технические параметры ниже — предлагаемая инженерная базовая линия M1, а не сведения из официальных правил; изменение оформляется через change request и ADR, если затронута архитектура. Ответственными до назначения конкретных людей являются роли.

Приоритет источников: решения владельца продукта определяют состав M1; официальные правила и подтверждённые тексты/исправления карт определяют партию. Разногласия между ними нельзя молча разрешать программированием нового правила: нужен ответ правообладателя и согласование продукта. Для выпуска фиксируются редакции правил, контента и решений. Обновление сайта не меняет уже запущенную партию.

## 2. Цели и измеримый результат

1. Два человека открывают браузер, соединяются через комнату и завершают полноценную партию без регистрации и установки.
2. Каждый выбирает любую из шести стартовых колод; все входящие карты работают по подтверждённым правилам, включая взаимодействия между фракциями и зеркальные встречи.
3. Сервер самостоятельно определяет допустимость действий, случайность, переходы состояния и результат. Клиент отображает персональную проекцию игры.
4. Разработка воспроизводима: версия правил, контента, протокола и сборки связана с тестами, результатами QA и выпуском.
5. Подготовлен путь к публикации на GamePix с отдельными техническими, контентными и правовыми воротами.

Продуктовая приёмка: все сценарии раздела 5 и критерии раздела 16 выполнены на staging; нет незакрытых блокирующих дефектов; все шесть колод подтверждены. Количество игроков и выручка не являются критериями M1. Согласование документа не означает завершения milestone.

## 3. Рамки

### 3.1 В M1

Браузерный клиент; анонимные сессии; приватные комнаты на двух участников; код и приглашение; выбор фиксированной колоды; расстановка Приказов; подготовка руки; полный игровой цикл; ручные решения, требуемые картами; журнал публичных событий; сдача; восстановление соединения; экран результата; новая партия по взаимному согласию; минимальная помощь по управлению; диагностируемый backend; публикационная сборка и комплект доказательств для GamePix.

Матч — ровно одна партия. Последующее согласие на реванш создаёт новый matchId с новой случайностью и подготовкой. Счёт серии, турнирная сетка и переходы Bo3 отсутствуют.

### 3.2 Вне M1

Коллекция, бустеры, торговля, инвентарь, редактор и импорт колод, дополнительная колода, замены, регистрация, пароли, социальный вход, профиль, постоянная история пользователя, рейтинг, подбор незнакомых соперников, боты, одиночная кампания, наблюдатели, чат, друзья, турниры, пользовательские скрипты, платные функции, реклама по инициативе игры, Xsolla и платёжные SDK. Не закладывать скрытые заглушки оплаты или зависимости на будущую регистрацию.

Не требуется реализовывать карты вне шести колод, кроме объектов, которые могут быть созданы их способностями. Такие создаваемые объекты входят в обязательное транзитивное покрытие DATA-05. Нельзя исключить сложную карту из опубликованной колоды ради завершения M1.

## 5. Пользовательские сценарии

| ID | Сценарий и ожидаемый результат |
| --- | --- |
| UC-01 | Игрок открывает страницу, читает краткую помощь, получает анонимную сессию и создаёт комнату. Видит код, приглашение и статус ожидания. |
| UC-02 | Второй игрок вводит код либо открывает приглашение. При свободном месте занимает второе место; третий получает понятный отказ. |
| UC-03 | Каждый выбирает колоду, изучает её состав и доступные описания, устанавливает порядок своих Приказов и подтверждает готовность. |
| UC-04 | После готовности обоих сервер создаёт матч, определяет инициативу и проводит подготовку. Каждый принимает решение о пересдаче; решения и чужая рука не раскрываются. |
| UC-05 | Игрок выполняет доступное действие, выбирает режим, цели, клетку и требуемую оплату. Сервер принимает команду либо возвращает причину отказа без частичного списания. |
| UC-06 | При обязательном или разрешённом выборе интерфейс явно показывает, кто и что должен решить. Партия не перескакивает через ручное решение из-за анимации. |
| UC-07 | Игроки наблюдают бой, последствия эффектов, Приказы и переходы фаз. Можно изучить открытые карты и публичный журнал. |
| UC-08 | При кратком обрыве игрок видит восстановление связи; после переподключения получает актуальную персональную проекцию и продолжает. |
| UC-09 | Игрок сдаётся через подтверждение внутри интерфейса. Сервер фиксирует единственный результат и показывает его обоим. |
| UC-10 | После партии оба соглашаются на новую. При отказе или уходе второй видит завершение ожидания; существующий результат не переписывается. |
| UC-11 | Неверный/просроченный код, заполненная комната, устаревшая версия клиента, недоступный сервер и утрата сессии дают отдельные понятные состояния и допустимый следующий шаг. |
| UC-12 | Игра в iframe, изменение размера, сенсорный ввод и возврат из скрытой вкладки сохраняют управляемость; платформенная политика проверяется отдельно по GP-03. |

## 6. Функциональные требования

### 6.1 Сессии и комнаты

| ID | Требование |
| --- | --- |
| FR-01 | Создавать анонимную сессию без email, номера телефона и учётной записи; экранное имя необязательно, допустимы серверные «Игрок 1/2». |
| FR-02 | Выдавать секрет восстановления места, не совпадающий с кодом комнаты. Код позволяет только запросить свободное место, но не забрать занятое. |
| FR-03 | Создание и присоединение атомарны; комната имеет ровно два места. Повтор запроса с тем же ключом не создаёт несколько комнат/мест. |
| FR-04 | Генерировать криптографически случайный код минимум из 10 символов алфавита размером 32; проверять коллизии. Не публиковать каталог комнат. |
| FR-05 | В собственной сборке формировать URL с кодом без секрета сессии; кодовый ввод работает при недоступном Clipboard API. В GamePix способ приглашения зависит от GP-03. |
| FR-06 | Пока матч не начался, участник может сменить колоду/порядок Приказов и снять готовность. Любое изменение сбрасывает его готовность; старт фиксирует версии и составы атомарно. |
| FR-07 | Разрешать зеркальную встречу. Перед стартом оба места заняты, сессии действуют, колоды валидны и оба игрока готовы. |
| FR-08 | Смена хозяина комнаты не нужна для управления матчем: состояние принадлежит серверу. Уход создателя из лобби не отключает оставшегося игрока. |
| FR-09 | Пустая комната удаляется через 15 минут, неактивное лобби — через 30 минут. Активный матч не удаляется по TTL лобби. Перед очисткой завершить ожидающие запросы с причиной. |
| FR-10 | Одно место имеет одно управляющее соединение. Новое соединение с действительным секретом вытесняет старое; старому запрещаются команды, утечка токена не скрывается как штатная ошибка игры. |

| FR-23 | После обнаруженного разрыва остановить принятие игровых команд и начать 120-секундное окно восстановления. Показать обоим публичный статус связи без деталей закрытого решения. |
| FR-24 | Успешный resume возвращает полный свежий снимок и тот же seatId; повтор принятой команды не повторяет эффект. Оставшееся время окна задаёт сервер. |
| FR-25 | По окончании окна один отсутствующий игрок получает техническое поражение; при отсутствии обоих — aborted_technical без победителя. Конкурирующие reconnect и timeout сериализуются одним владельцем матча. |
| FR-26 | Чтобы повторные разрывы не останавливали матч бесконечно, бюджет ожидания — 300 секунд на игрока за матч; каждое окно ограничено минимумом из 120 секунд и остатка бюджета. Порог — политика сервиса, подлежащая продуктовому согласованию OQ-03. |
| FR-27 | Общий игровой таймер и автопас не вводятся до OQ-03. Неактивность 15 минут вызывает предупреждение; 30 минут без принятого решения завершают матч aborted_technical, без присуждения игровой победы. Это эксплуатационный лимит, явно сообщаемый до старта. |
| FR-28 | Перезапуск процесса в базовой однопроцессной реализации завершает потерянные матчи технически; UI объясняет отсутствие восстановления. Если требуется переживать рестарт, это отдельное решение ADR до реализации OPS-04. |

Параметры FR-22–28 не выдаются за официальные правила. Их принятие владельцем продукта требуется до публичного выпуска; допускается пересмотр без изменения механики карт. Отключение таймеров клиента не влияет на серверные сроки.

Требуемая запись карточного определения (схема, не выдуманная карта):

```text
CardDefinition {
  cardId, setCode, printedNumber, locale, name,
  types[], subtypes[], supertypes[], factions[],
  cost: ValueExpression | NotApplicable | Unknown,
  stats: { influence?, strength?, durability? },
  faces[{ faceId, level?, exactAbilityText, abilityIds[] }],
  effectSpecVersion, imageAssetId?, verificationStatus,
  evidence[{ fieldPath, sourceUrl, sourceRevision?, checkedAt, reviewer }]
}
```

Неприменимые поля отмечаются явно. Приведённые таблицы составов не заменяют CardDefinition и не являются доказательством полной карточной базы. На дату документа подтверждённых полных определений нет; это блокирует завершение M1, но не подготовку архитектуры и спецификации.

## 8. Игровые механики и нормативное покрытие

### 8.1 Нормативная основа

RULE-01: реализовать партию по S1 и проверенным карточным текстам, без упрощения до привычных механик других ККИ. В частности, нельзя автоматически подменять очередь стеком LIFO или считать силу обычными отдельными очками здоровья.

Краткая ориентация по S1: стартовая рука — семь карт; предусмотрена однократная пересдача. Фазы: начало, взятие, действие, бой, конец, затем восстановление. Взятие первого хода пропускается. В действии у каждого пять решений, пас расходует действие; два последовательных паса завершают фазу. Поле содержит пять линий; направление боя связано с инициативой. Приказы участвуют в условиях поражения; пустая колода также требует их обработки. Для точной процедуры подготовки, столкновений, оплаты, очереди, восстановления, информационных состояний и терминов применяется S1; таблица ниже задаёт проверку реализации, а не новую редакцию правил.

### 8.2 Реестр обязательных наборов тестов

Каждый набор должен ссылаться на конкретный заголовок S1 и версию правил. До реализации QA и rules reviewer утверждают входное состояние, решение игрока и ожидаемые события. Если источник допускает неоднозначное толкование, тест помечается blocked с OQ, а не закрепляет догадку как правило.

| ID | Нормативная область S1 | Обязательные границы проверки |
| --- | --- | --- |
| RULE-02 | Начало игры; Инициатива | Обе стартовые инициативы, все перестановки позиций на уровне модели, выбор нуля/части/всей руки при подготовке, повторное решение и неподходящий момент |
| RULE-03 | Фазы хода | Все переходы, действие каждого места, исчерпание действий, последовательность пасов, эффекты на границах фаз; клиент не управляет переходом напрямую |
| RULE-04 | Виды карт; Игровые зоны | Каждая допустимая зона и тип, занятая/недопустимая клетка, смена контроля, временный просмотр и скрытое состояние |
| RULE-05 | Розыгрыш карт; Активируемые способности | Все стадии, отсутствие цели, изменение цели, недостаточная оплата, альтернативная/дополнительная стоимость, откат недопустимой операции без частичных изменений |
| RULE-06 | Триггерные способности; Очередь | Несколько одновременных объектов обоих игроков, выбор их порядка, новые эффекты во время разрешения, исчезновение источника/цели, обязательный и добровольный выбор |
| RULE-07 | Фаза боя | Обе ориентации поля, каждая линия, симметричное/асимметричное столкновение, прерывающие эффекты, появление/перемещение объекта во время боя |
| RULE-08 | Приказ; Конец игры | Все пять позиций, повторное использование физического объекта после раскрытия, отсутствие доступного Приказа, одновременные требования обоим игрокам, эффект победы/поражения |
| RULE-09 | Восстановление; постоянные и временные эффекты | Пересчёт после события, окончание длительности, смена инициативы, сброс поворота, базовые значения и модификаторы |
| RULE-10 | База знаний | Каждое встречающееся в контенте ключевое слово отдельно и во взаимодействии; неприменимые ключевые слова перечислены с доказательством отсутствия |

Обязательный словарь для анализа покрытия: Призыв, Смерть, Обход, Стойкость, Магический щит, Натиск, Яд, Дальняя атака, Активация, Ритуал, Всадник, Дань, Пожертвовать, Пропуск боя, Усиленный юнит, жетоны, замещения, отложенные триггеры, выбор режимов. Наличие термина в словаре не означает, что подтверждено его наличие в конкретной стартовой колоде.

RULE-11: вести отдельную таблицу «норма → реализация → тест → результат» и «карта/способность → сценарии». Покрытие измеряется не только строками кода. Нетестируемая или неподтверждённая способность блокирует приёмку соответствующего контента и всего M1.

RULE-12: при потенциально бесконечной цепочке сервер применяет технический предохранитель, например 10 000 внутренних событий на одну команду: сохраняет диагностический trace и завершает матч как aborted_technical. Это защита процесса, не объявление победы и не придуманное правило ничьей. Конкретный предел подтверждается нагрузочными тестами и ADR.

### 8.3 Состояние игрового автомата

```text
Room: waiting -> preparing -> active -> finished -> expired
                         \-> cancelled
Match: setup -> order_selection -> mulligan -> playing -> finished
Playing: start -> draw -> action -> combat -> end -> recovery -> start
Combat: start_combat -> lane_step[1..5] -> end_combat
```

Это техническая декомпозиция. Названия setup/order_selection не задают дополнительного публичного игрового действия. Вход в подшаг допускается только если выполнены нормативные условия; pendingChoice может приостановить автоматическое продвижение в любом допустимом месте. Состояние связи хранится отдельно, чтобы reconnect не сбрасывал фазу.

| Объект | Минимальные поля и инварианты |
| --- | --- |
| MatchState | matchId, версии, revision, статус, turnNumber, phase, combatStep, initiativeSeat, actingSeat, result; один последовательный писатель |
| PlayerState | seatId, hero, влияние, список экземпляров по зонам, позиции, использованные Приказы, бюджет действий/связи, приватные решения |
| Board | Физические стороны A/B, laneId 0..4, клетки unit/support, location; функция отображения относительно инициативы и точки зрения |
| CardInstance | instanceId для аудита, definitionId, ownerSeat, controllerSeat, zone, zoneObjectId/generation, face, положение, поворот, жетоны, базовые/вычисленные характеристики |
| EffectState | effectId, sourceRef, targetRefs, длительность, слои модификаторов, отложенные условия; детерминированный порядок обработки |
| Queue | Упорядоченные записи entryId, источник, выбранные режимы, цели, оплата и контекст; без скрытого LIFO |
| PendingChoice | choiceId, адресат, тип, допустимые варианты, ограничения, версия; публичная форма не раскрывает приватные варианты |
| RandomState | Серверный seed/состояние генератора и cursor; недоступен клиентам и публичным логам |
| AuditState | Принятые команды, результаты случайности, события, версии и технические причины окончания; доступ ограничен |

RULE-13: ownerSeat, controllerSeat и адресат эффекта — разные понятия. Перемещение между зонами создаёт новую ссылочную идентичность zoneObjectId; постоянный instanceId нужен только аудиту и не позволяет старой цели воздействовать на новый объект. Публичный идентификатор закрытого объекта не должен позволять отследить его через перемешивание.

RULE-14: переход выполняется транзакционно: проверка входа → вычисление → проверки состояния/эффекты → допустимые решения → события/проекции → фиксация. Если требуется пользовательский выбор, сохраняется устойчивое pendingChoice, а не удерживается незавершённая сетевая транзакция. Неопределённые значения и порядок обхода Go map не могут влиять на исход.

RULE-15: контрольные инварианты выполняются после каждой принятой команды и внутреннего события: объект не находится в двух зонах; клетка не занята дважды; ссылка соответствует поколению; счётчик действий не отрицателен; результат единственный; обязательный выбор не теряется. Исключения, разрешённые картой, моделируются явно.

## 9. Сетевая модель и контракты

### 9.1 Транспорт и API

NET-01: HTTP JSON для сессии/лобби, WSS JSON для активного состояния и команд. UTF-8, время UTC RFC3339 для диагностики; длительности в миллисекундах, игровые числа — целые либо явно типизированные выражения. Клиентские часы не определяют игровой исход.

| Метод/путь | Назначение | Основной результат |
| --- | --- | --- |
| POST /api/v1/sessions | Создать анонимный контекст | sessionId и защищённый секрет; Cache-Control: no-store |
| POST /api/v1/rooms | Создать комнату с Idempotency-Key | roomId, code, собственное место, invitation metadata |
| POST /api/v1/rooms/join | Атомарно занять место по code | roomId, seatId или безопасный отказ |
| GET /api/v1/rooms/{roomId} | Свой статус лобби | Персональная проекция, без секретов соперника |
| POST /api/v1/ws-tickets | Получить одноразовый билет | Билет на 30 секунд для upgrade; связан с session/seat |
| GET /api/v1/ws | WebSocket upgrade | Проверенный канал; билет передаётся в первом auth-сообщении за 5 секунд |
| GET /health/live | Жив ли процесс | Без внутренних подробностей |
| GET /health/ready | Готов ли принимать новые матчи | Проверка доступности обязательных зависимостей |

NET-02: билет не помещать в URL или логи. До аутентификации соединение не получает комнатные данные и не принимает игровые команды. HTTP-аутентификация для standalone — защищённая host-only HttpOnly cookie и CSRF-защита. Для iframe при блокировке third-party cookies нужен отдельный проверенный способ хранения/передачи bearer-секрета через platform adapter; он решается в ADR и DEP-04 до GamePix release. Нельзя просто отключить проверку Origin ради iframe.

### 9.2 Конверты сообщений

Пример команды; идентификаторы синтетические, содержимое не является реальной картой:

```json
{
  "protocolVersion": "1.0",
  "type": "command",
  "commandId": "01-command-example",
  "matchId": "01-match-example",
  "expectedRevision": 42,
  "name": "submitChoice",
  "payload": {
    "choiceId": "choice-example",
    "optionIds": ["option-example"]
  }
}
```

```json
{
  "protocolVersion": "1.0",
  "type": "commandResult",
  "commandId": "01-command-example",
  "accepted": true,
  "revision": 43,
  "eventSeq": 108
}
```

NET-03: клиентские команды: selectDeck, setOrderArrangement, setReady, submitMulligan, playCard, activateAbility, passAction, submitChoice, surrender, requestRematch, leaveRoom, resync. Все имеют схемы payload; playCard содержит sourceObjectId, declaredType, modeIds, targetRefs, placement и paymentChoice, когда они нужны. Присылать seed, итог силы, результат боя или новую фазу запрещено. Список карт и готовое состояние клиента сервер не принимает.

NET-04: серверные типы: authenticated, roomSnapshot, matchSnapshot, stateUpdate, choiceRequested, commandResult, error, connectionStatus, matchFinished, serverDraining. Событие содержит eventSeq и revision. Для M1 допустимы полные персональные снимки вместо сложного delta; при delta обязательны baseRevision и полный resync при разрыве последовательности. Heartbeat имеет отдельный тип и не увеличивает игровую revision.

NET-05: accepted означает, что команда зафиксирована сервером, а не что анимация закончена. Для отклонённой команды состояние и revision не изменяются. commandId уникален в пределах сессии/матча; повтор с тем же payload возвращает прежний результат, с другим — COMMAND_ID_REUSED. Кеш результатов живёт весь матч и ещё 15 минут после него; после очистки завершённый матч всё равно не принимает команд.

NET-06: команды одного матча сериализуются. Сверять expectedRevision, текущего адресата решения, полномочия seat и легальность. При STALE_REVISION вернуть свежую персональную проекцию или требование resync; клиент не переотправляет опасную команду автоматически с новой revision. Конкурирующие ready/start не создают два матча.

NET-07: коды ошибок: INVALID_PAYLOAD, UNAUTHENTICATED, FORBIDDEN, ROOM_UNAVAILABLE, ROOM_FULL, MATCH_FINISHED, NOT_YOUR_DECISION, ILLEGAL_ACTION, INVALID_TARGET, INSUFFICIENT_COST, STALE_REVISION, CHOICE_EXPIRED, COMMAND_ID_REUSED, RATE_LIMITED, VERSION_UNSUPPORTED, SERVER_UNAVAILABLE. Error включает code, retryable, correlationId и локализуемый messageKey; закрытая причина допустимости не раскрывается. HTTP использует 400/401/403/404/409/422/429/503 по смыслу, без stack trace.

NET-08: reconnect с backoff 0.5/1/2/4/8 секунд, затем максимум 10 секунд с jitter; не позднее серверного дедлайна. Resume содержит lastEventSeq как подсказку, сервер всегда вправе отправить snapshot. Потеря браузерного секрета означает потерю возможности восстановления места, а не восстановление по коду комнаты.

NET-09: OpenAPI для HTTP и JSON Schema/AsyncAPI для WebSocket обязательны в репозитории до сетевой реализации. Примеры проходят schema validation; TypeScript-типы генерируются либо проверяются на согласованность с Go. Несовместимые изменения повышают major протокола. Устаревший клиент до старта получает предложение обновиться; активный матч обслуживается совместимой серверной версией до завершения или явно технически прекращается при аварии.

### 9.3 Персональные проекции

NET-10: клиент получает только PlayerView, никогда сырой MatchState. Отдельная allowlist-сериализация определяет открытые сведения, собственные личные сведения и разрешённые временные просмотры. Скрытые данные не отправляются «для удобства UI» даже под флагом hidden.

NET-11: неизвестная карта передаётся как безопасное представление рубашки/количества без definitionId, abilityIds, seed, внутреннего instanceId и полей, позволяющих восстановить порядок колоды. Известный состав фиксированной колоды сам по себе не разрешает раскрыть текущую руку, порядок или закрытый выбор. Разрешённое правилами раскрытие получает явно ограниченную аудиторию и срок; replay для игрока подчиняется той же политике.

## 10. Архитектура

Начальный выбор — модульный монолит Go и отдельная статическая React/TypeScript-сборка. Это план M1, а не описание существующего кода. Микросервисы, Kafka и распределённый game state в M1 не требуются.

```text
React/TypeScript UI -> HTTP/WSS gateway -> session/room application service
                                           |
                                     match owner (Go)
                                           |
                          deterministic engine + versioned content
                                           |
                              audit / metrics / diagnostics
Platform adapter: standalone | GamePix (изолирован от engine)
```

| Граница | Обязанность |
| --- | --- |
| engine | Чистые правила и переходы, валидация, эффекты, RNG как зависимость; без HTTP, React и SDK |
| content | Схемы, определения, manifests, происхождение, валидация и версии |
| application | Жизненный цикл комнат/матчей, анонимные полномочия, таймеры и идемпотентность |
| transport | HTTP/WSS, схемы, лимиты, персональные проекции, корреляция |
| frontend | View model, взаимодействия, визуализация, доступность, reconnect; без авторитетной симуляции |
| platform | Загрузка, язык, хранение и lifecycle GamePix; standalone работает без глобального SDK |
| operations | Деплой, TLS, наблюдаемость, выпуск, откат, конфигурация |

NFR-01: один match owner последовательно обрабатывает mailbox событий. RNG и время вводятся зависимостями; shuffle использует серверную случайность с криптографически случайным seed. Одинаковые начальное состояние, версии, seed/случайные результаты и команды дают одинаковый итоговый хеш. Производственный seed закрыт; тестовые seed воспроизводимы.

NFR-02: типизированные effect handlers или ограниченный декларативный DSL; никакого eval и удалённого исполнения карточного текста. Операции со ссылками на объекты проверяют поколение и права доступа.

NFR-03: рекомендуемая будущая структура: backend/cmd/server, backend/internal/engine, backend/internal/application, backend/internal/transport, frontend, content, contracts, docs/adr, docs/runbooks, tests. Эти каталоги создаются по мере реализации; текущая задача добавляет только документацию.

## 15. Стратегия тестирования

### 15.1 Уровни

1. Unit: чистые переходы, инварианты, оплата, цели, RNG, каждый effect handler и все RULE-наборы.
2. Property/fuzz: случайные последовательности только допустимых действий; сохранение инвариантов, воспроизводимость, отсутствие panic, защита от некорректного JSON и ссылок.
3. Card conformance: каждая способность каждой карты — положительный сценарий, отказ/граница, взаимодействие с типовыми модификаторами и сменой зоны. Подтверждает rules reviewer, а не только автор кода.
4. Integration: HTTP/WSS с двумя сессиями, третий join, race старта, дубликаты, stale revision, восстановление и технические таймеры с виртуальными часами.
5. Contract: схемы запросов/ответов, совместимость Go/TypeScript, невозможность сериализовать секреты в PlayerView.
6. E2E: два независимых браузерных контекста от комнаты до результата; тесты не читают приватное состояние соперника для выполнения пользовательских шагов.
7. Security/load/resilience: сценарии SEC, NFR-09–13, переполнение буферов, падение одного матча и рестарт.
8. Manual acceptance: читаемость карт, касание, клавиатура, iframe и GamePix testkit, сверка с экспертом по правилам.

### 15.2 Матрица и доказательства

QA-матрица включает 36 упорядоченных сочетаний deckA × deckB (в том числе шесть зеркал). Для каждого — сценарий полного завершения и обе стартовые инициативы, всего минимум 72 воспроизводимых прогона. Это smoke взаимодействия, а не доказательство покрытия всех комбинаций способностей. Отдельные tests покрывают каждую карту и выявленные пары эффектов с повышенным риском.

До release обязательны: 100% abilityId из manifests связаны с прошедшими conformance-тестами; все RULE-наборы пройдены; engine branch coverage целевое ≥85%, с обоснованием непокрытых ветвей; отсутствие необъяснённых flaky тестов. Покрытие строк не заменяет семантическую сверку.

Каждый дефект содержит версии, seed или закрытый trace с ограниченным доступом, минимальную последовательность команд, ожидаемый нормативный исход и фактический исход. Исправление игрового дефекта сопровождается regression test. Публичный баг-репорт не публикует секреты и скрытые карты активного матча.

Для документации проверяются структура Markdown, ссылки/локальные пути, уникальность ID, согласованность перекрёстных ссылок и арифметика составов. Тесты приложения для изменения только документа не заявляются как выполненные.

## 19. Корпоративный процесс разработки

### 19.1 Управление требованиями

PROC-01: каждая задача backlog ссылается на ID требования, содержит acceptance criteria, владельца, зависимости, оценку и evidence для завершения. Для карточных задач обязательны cardId/abilityId и подтверждённый источник. Изменения scope оформляются отдельным решением с влиянием на сроки, тесты и публикацию.

PROC-02: ADR хранить в docs/adr/NNNN-title.md: контекст, решение, альтернативы, последствия, статус и ссылки на требования. Первые ADR: модульный монолит/границы engine; последовательность матча и детерминизм; протокол/проекции; сессии и iframe; долговечность состояния; lifecycle GamePix. ADR не заменяет официальный ruling по правилам.

### 19.2 Ветки и review

PROC-03: main — интеграционная ветка с зелёными проверками; короткоживущие feature/*, fix/*, docs/* от актуального main. Перед работой проверять status/diff, учитывать чужие изменения, не использовать принудительное переписывание опубликованной истории. Незавершённые чужие файлы не включать в свои коммиты.

PROC-04: для разработки — PR в main, минимум один независимый review; для правил/контента — дополнительно rules/content reviewer. Автор не считается независимым проверяющим. Защитить main от force push, потребовать CI и закрытие обсуждений; конкретные настройки репозитория выполняются отдельно с полномочиями администратора.

PROC-05: Conventional Commits: feat(engine): ..., fix(protocol): ..., docs(requirements): ..., test(content): ..., ci: .... Коммит содержит связное изменение; squash либо обычное слияние выбирается командой и фиксируется в contributing. Предлагаемый default — squash PR; releases помечаются version tag и manifest.

Для первой документационной задачи владелец продукта явно разрешил отдельную ветку и последующее прямое слияние в main. Это bootstrap-исключение, а не утверждение, что независимый review уже проведён. Если защита main требует PR, следовать защите и сообщить незавершённое слияние; не обходить ограничения.

### 19.3 CI

PROC-06: каждый PR запускает проверку формата/линтеров, Go unit и race tests, TypeScript typecheck, frontend tests/build, schema/contract checks, content validation, secrets/dependency scanning и целевые integration tests. Полная матрица матчей и нагрузка могут идти nightly/release, но обязательны для release candidate. Точные команды и версии инструментов фиксируются при создании scaffold; этот документ не выдаёт их за существующий pipeline.

PROC-07: CI публикует отчёты и immutable artifacts с commit SHA. Ошибка обязательного шага блокирует merge; flaky тест не отключается без issue, владельца и срока. Для docs-only допустим отдельный набор Markdown/link/consistency checks без бессмысленного запуска отсутствующего приложения.

### 19.4 Definition of Ready / Done

Задача готова к реализации, когда понятны требование, входные данные, ожидаемый исход, зависимости и способ проверки; для игровой механики есть ссылка на норму и утверждённые примеры.

Задача завершена, когда изменение реализовано, проверено соответствующими тестами, прошло review, документация/контракты обновлены, нет утечек секретов, CI зелёный, acceptance evidence приложены и всё влито в main. Для UI добавляется проверка браузеров/доступности по риску; для карты — verification и conformance; для эксплуатации — runbook и откат.

Milestone завершён только по разделу 16; отдельные зелёные задачи не компенсируют отсутствие одной из шести колод или незакрытые блокирующие зависимости.

## 20. Последовательность реализации и комплект поставки

1. Согласовать спецификацию, назначить роли, собрать данные и разрешения, открыть DEP/OQ в backlog.
2. Создать scaffold, ADR, схемы контента/протокола, CI и проверяемый engine skeleton. Параллельно организационно уточнить GamePix; это не разрешение подменить неизвестные карточные данные.
3. Реализовать ядро с тестовыми fixtures, затем подтверждённые способности и полные шесть manifests; вести покрытие требований.
4. Реализовать сессии, комнаты, WSS, персональные проекции, reconnect и UI полного сценария.
5. Провести card conformance, 72 smoke-прогона, безопасность, нагрузку, устройства и staging soak; устранить блокирующие дефекты.
6. Собрать release evidence, подтвердить core acceptance; пройти GamePix gate, выполнить подачу и зафиксировать фактический статус публикации.

Поставляемые артефакты M1: Go backend, React/TypeScript frontend, полная проверенная карточная база и manifests, OpenAPI/WS schemas, тесты/матрицы/отчёты, ADR, инструкции local/staging/prod, runbooks, asset/license register, release manifest, GamePix package и подтверждение статуса площадки. В текущей документационной поставке создаются эта спецификация и ссылка из README; перечисленные программные артефакты остаются будущей работой.
