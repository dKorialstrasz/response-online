# ADR-0002: Границы модульного монолита M1

- Статус: принято
- Дата: 17 октября 2026 года
- Решение: владелец проекта dKorialstrasz
- Связанные требования: NFR-02–03, PROC-02, OPS-02, AC-10
- Связанная задача: [#8](https://github.com/dKorialstrasz/response-online/issues/8)

## Контекст

M1 должен локально запускать Go backend и статический React/TypeScript клиент.
Микросервисы, распределённое состояние, публичный deployment и GamePix не входят
в согласованный scope. При этом игровое ядро нельзя связывать с HTTP, UI или
будущим SDK площадки.

## Решение

Backend реализуется как один Go-модуль и один процесс с внутренними границами:

- `engine` — детерминированные правила и переходы; время и энтропия только через
  переданные зависимости;
- `application` — жизненный цикл комнат/матчей и последовательные match owners;
- `transport` — HTTP/WSS, проверка входов и персональные представления;
- `buildinfo` — идентичность локальной сборки без игрового состояния.

`engine` не импортирует application/transport. `application` может использовать
engine, а transport — application. Frontend собирается отдельно и считает сервер
единственным авторитетным источником состояния. `content` и `contracts` остаются
версионируемыми артефактами на верхнем уровне репозитория.

Issue #8 создаёт только диагностический HTTP surface и инфраструктурные порты.
Игровые правила, карточные эффекты, сессии, комнаты и WebSocket-команды появляются
только в соответствующих roadmap issues.

## Последствия

- Один локальный процесс проще воспроизводить и диагностировать.
- Пакеты можно тестировать без сети и React.
- Будущий platform adapter не получает доступ к engine и не меняет правила.
- Горизонтальное масштабирование и выделение сервисов потребуют нового ADR.

## Рассмотренные альтернативы

- Микросервисы отклонены как преждевременное усложнение M1.
- Выполнение карточного текста или общий `eval` запрещены NFR-02.
- Встраивание React-ресурсов в Go binary пока отложено: локальная разработка и
  immutable CI-артефакты не требуют такого связывания.
