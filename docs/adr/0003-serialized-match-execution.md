# ADR-0003: Последовательное выполнение матча

- Статус: принято
- Дата: 17 октября 2026 года
- Решение: владелец проекта dKorialstrasz
- Связанные требования: NFR-01, NFR-11, PROC-02, OPS-04
- Связанная задача: [#8](https://github.com/dKorialstrasz/response-online/issues/8)
- Учитывает: [ADR-0001](0001-in-memory-match-state.md)

## Контекст

Параллельная обработка действий одного матча создаёт недетерминированные гонки.
M1 хранит активное состояние только в памяти и честно теряет его при crash или
restart. Нужно определить порядок исполнения, не утверждая ещё не реализованные
правила игры.

## Решение

Каждый активный матч получает ровно одного owner. Входящие операции помещаются в
ограниченный mailbox и исполняются owner последовательно. Только owner изменяет
состояние матча. HTTP/WSS handlers не мутируют engine напрямую.

Время и энтропия передаются engine через интерфейсы. Будущая реализация сохраняет
seed или уже полученные случайные результаты в закрытом trace; production seed не
попадает в публичные ответы и общие журналы. Команда несёт id и ожидаемую ревизию,
когда эти поля будут определены protocol issue. Повтор, stale revision и переполнение
mailbox завершаются контролируемым ответом, а не параллельной мутацией.

Scaffold содержит generic `MatchOwner` и race-тест последовательности. Он не
реализует игровые команды и не задаёт результат партии.

## Последствия

- Порядок операций одного матча воспроизводим.
- Разные матчи могут выполняться независимо.
- Долгая операция блокирует свой mailbox; для неё потребуются измеримые бюджеты.
- Crash процесса остаётся полной потерей активного матча согласно ADR-0001.

## Рассмотренные альтернативы

- Общий mutex вокруг всех матчей отклонён: он связывает независимые партии.
- Параллельная мутация одного state отклонена из-за гонок и невоспроизводимости.
- Durable event log отложен за пределы локального M1 согласно ADR-0001.
